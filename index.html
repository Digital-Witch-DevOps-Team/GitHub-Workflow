1. Workflow at a glance

Use the following route for every assignment. Feature work is developed on a branch, reviewed in a pull request, and only then integrated into the shared branch.

2. Senior: initialise the organisation repository

Run once from a parent folder where the project folder should be created. The organisation repository should already exist. Ideally it is empty when importing an existing Git history; if it contains independent commits, stop and reconcile the histories instead of force-pushing.

# Clone the original/source project
git clone https://github.com/digitalwitchdemo/Final-Project-architecture-EKS-terraform.git
cd Final-Project-architecture-EKS-terraform

git status
git branch --show-current

# Configure this repository only (no --global)
git config user.name "YOUR GITHUB USERNAME"
git config user.email "YOUR GITHUB NOREPLY EMAIL"

# Keep source as upstream; use the organisation repository as origin
git remote rename origin upstream
git remote add origin https://github.com/Digital-Witch-DevOps-Team/Terraform-Infrastructure-as-code-IaC.git
git remote -v

# Assumes the source branch is named main
git push -u origin main
git switch -c Dev-Team
git push -u origin Dev-Team

4. Junior developer: fork, branch, and submit work

Step A — Fork on GitHub

  1. Open the organisation repository and click Fork.
  2. Choose your personal GitHub account as the owner, for example Ose-Jossy.
  3. Keep the repository name Terraform-Infrastructure-as-code-IaC unless the team says otherwise.
  4. Uncheck Copy the default branch only if you want all branches copied. This is optional for the workflow because you will fetch `Dev-Team` from the organisation remote.
  5. Click Create fork.

Step B — Clone the junior's fork

git clone https://github.com/JUNIOR-USERNAME/Terraform-Infrastructure-as-code-IaC.git
cd Terraform-Infrastructure-as-code-IaC
git status
git branch --show-current

Step C — Add the organisation as `upstream`

git remote add upstream https://github.com/Digital-Witch-DevOps-Team/Terraform-Infrastructure-as-code-IaC.git
git remote -v
git fetch upstream
git branch -r
Remote in junior cloneMust point to
originThe junior's personal fork
upstreamThe organisation repository
upstream/Dev-TeamOrganisation branch to base feature work on

The origin/* branches vary depending on the fork options. The key check is that git fetch upstream makes upstream/Dev-Team available.

Step D — Configure identity and create a feature branch

# Set identity for this clone only
git config user.name "YOUR GITHUB USERNAME"
git config user.email "YOUR GITHUB NOREPLY EMAIL"
git config --local --list

# Branch from the organisation's Dev-Team
git switch -c feature/update-terraform upstream/Dev-Team
git branch
git status

Use a new task-specific branch for each assignment, for example feature/add-vpc-module or docs/update-deployment-guide.

Step E — Review, stage, commit, and push

# Edit assigned files in VS Code, then inspect changes
git status --short

# Stage only the intended files
git add path/to/changed-file1 path/to/changed-file2
git diff --cached

git commit -m "Add short description of change"
git push -u origin feature/update-terraform
Never commit secrets. Do not stage real .env, atlas.credentials.env, cloud credentials, access keys, private keys, passwords, tokens, or Terraform state files. Ignore sensitive local files with .gitignore and use safe placeholder values in .env.example. If a secret was committed or pushed, revoke/rotate it immediately; deleting the file later is not enough.

Example patterns to review and adapt in the repository's .gitignore (keep any existing project rules you need):

# Local environment and credential files
.env
.env.*
!.env.example
atlas*.env
*.pem
*.key

# Terraform local state/cache; follow the team's state-management policy
.terraform/
*.tfstate
*.tfstate.*

5. Senior: review and merge into `Dev-Team`

  1. Open the PR in the organisation repository using a senior reviewer account with write access.
  2. Read the PR description and inspect Files changed.
  3. Check correctness, secrets, infrastructure/configuration, documentation, and evidence of testing.
  4. Select Review changes → Approve → Submit review when ready.
  5. Resolve required checks and review requests. Merge only when GitHub permits it.

The junior author and approving reviewer should be different accounts for this team's workflow. The approval must be a formal Approve review, not just a conversation comment.

Update the senior's local `Dev-Team`

git status
git fetch origin
git switch Dev-Team
git pull --ff-only origin Dev-Team
git log -5 --oneline
git status

Inspect the files that actually changed and run the project's required tests. For the practice example, cat junior-work.txt reads that file if it exists.

No push is needed to receive the junior's PR after it has been merged on GitHub. Fetch and pull update the senior's local branch.

6. Senior: promote tested `Dev-Team` into `main`

Refresh both local branches

git fetch origin
git switch main
git pull --ff-only origin main
git switch Dev-Team
git pull --ff-only origin Dev-Team

# Optional: summarise differences between the remote branches
git diff --stat origin/main...origin/Dev-Team

These commands update the senior's local branches. They do not merge `Dev-Team` into `main`.

Create the promotion PR on GitHub

  1. Open the organisation repository → Pull requests → New pull request.
  2. Set Base / destination to main.
  3. Set Compare / source to Dev-Team.
  4. Suggested title: Promote tested Dev-Team changes to main.
  5. Summarise the work and tests; create the PR.
  6. Review changed files/checks, obtain the required approval, and merge only when permitted.
  7. After merging, update local `main`:
git switch main
git pull --ff-only origin main
Do not shortcut protection: avoid git merge Dev-Team followed by git push origin main while `main` protection is active. The PR preserves the required reviews and rules.

Senior needs to contribute a change?

Use a working branch instead of direct commits to the protected `Dev-Team` branch:

git fetch origin
git switch Dev-Team
git pull --ff-only origin Dev-Team
git switch -c senior/update-practice-file

# Edit files, then stage only intended paths
git status --short
git add path/to/changed-file
git diff --cached
git commit -m "Update development configuration"
git push -u origin senior/update-practice-file

Open a PR with Base: `Dev-Team` and Compare: `senior/update-practice-file`, then review and merge under the same rules.

7. Non-negotiable team rules

RuleWhy it matters
Do not commit directly to `main`.Releases must go through the review workflow.
Use pull requests for changes to protected `Dev-Team`.Reviews catch mistakes before integration.
Never commit credentials, `.env` secrets, private keys, tokens, or Terraform state.Secrets can remain exposed in repository history after a file is deleted.
Check `git status --short` and `git diff --cached` before a commit.Prevents unrelated or sensitive files from being committed accidentally.
Run `git remote -v` before pushing if uncertain.Prevents pushing to the wrong repository.
Do not use force-push to work around a rejected push.Force pushes can discard collaborators' history.
If `git pull --ff-only` fails, stop and inspect status/history.A failed fast-forward may mean the local branch diverged; do not reset blindly.
Use one feature branch per task, meaningful commits, and clear PR descriptions.Makes review and project tracking easier.
